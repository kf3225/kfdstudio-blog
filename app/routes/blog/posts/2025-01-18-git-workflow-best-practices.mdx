# Git ワークフローのベストプラクティス

効果的なGitワークフローは、チーム開発の生産性を大きく向上させます。この記事ではベストプラクティスを紹介します。

## ブランチ戦略

### Git Flow

Git Flowは、長期運用されているプロジェクトに適したブランチ戦略です。

```
master (production)
  ↑
develop (integration)
  ↑
feature/* (新機能)
hotfix/* (緊急修正)
release/* (リリース準備)
```

### GitHub Flow

GitHub Flowは、継続的デリバリーを行うプロジェクトに適しています。

```
main (production)
  ↑
feature/* (新機能)
```

### 選択のポイント

- **Git Flow**: リリースサイクルが長い、複数のバージョンを維持する必要がある
- **GitHub Flow**: 頻繁なデプロイ、シンプルなプロセスを好む

## コミットメッセージの規約

### Conventional Commits

コミットメッセージを構造化することで、自動化と可読性を向上させます。

```
<type>(<scope>): <subject>

<body>

<footer>
```

主なtype:

- `feat`: 新機能
- `fix`: バグ修正
- `docs`: ドキュメント変更
- `style`: コードスタイル（機能への影響なし）
- `refactor`: リファクタリング
- `test`: テスト追加・修正
- `chore`: ビルドプロセスやツールの変更

### 実例

```
feat(auth): add JWT authentication

- Implement login endpoint
- Add token validation middleware
- Update user model

Closes #123
```

## プルリクエストの作成

### 良いプルリクエストの要件

1. **明確なタイトル**: 何が変更されたか一目でわかる
2. **詳細な説明**: 変更の理由、実装方法、影響範囲
3. **関連するIssue**: Issue番号を参照
4. **適切なレビュアー**: 関係者をアサイン
5. **CIの成功**: テストとLintがすべて通っていること

### テンプレート例

```markdown
## 概要

- [ ] 新機能
- [ ] バグ修正
- [ ] リファクタリング
- [ ] ドキュメント更新

## 変更内容

- 変更点1
- 変更点2
- 変更点3

## スクリーンショット

(該当する場合)

## テスト方法

1. 手順1
2. 手順2

## 関連Issue

Closes #123
```

## コードレビューのガイドライン

### レビュアー向け

- 建設的なフィードバックを心がける
- 小さなプルリクエストを目指す（< 400行）
- 重要な部分に集中する
- 自動フォーマットツールを使用してスタイル議論を減らす

### オーサー向け

- フィードバックに素早く対応する
- 議論が必要な場合は対話を求める
- レビューの感謝を示す

## リベース vs マージ

### リベース（推奨）

```bash
git checkout feature-branch
git fetch origin
git rebase origin/main
```

- 履歴が直線的でクリーン
- マージコミットが不要
- コンフリクト解決が一度で済む

### マージ

```bash
git checkout main
git merge feature-branch
```

- 履歴が正確に保持される
- ブランチのマージタイミングが明確

## まとめ

効果的なGitワークフローは、プロジェクトの特性に合わせて調整する必要があります。チームで合意を形成し、一貫性を保つことが重要です。
